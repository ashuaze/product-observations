# GitHub 草稿 PR：什么时候该请人接手评审？

- 原期号：P34
- 日期：2026-11-10（北京时间）
- 研究主题：协作交接与责任（P34–P40）。多人协作中，产品怎样让下一棒知道该做什么？
- 读者价值：用草稿与正式评审的对照，决定何时只分享进展、何时请一个人拍板、何时发起完整评审。

同一份改动可以让别人先看到，同时把评审请求留到合适的时点。若有一项决定卡住作者，草稿也需要明确的求助入口。GitLab 默认保留草稿流水线，是将自动反馈与人工评审分开的实例。

证据边界：官方文档支持状态、请求及流水线规则；效率与等待的权衡是待验证的产品推断。关键参考：[GitHub 草稿 PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[GitHub 代码负责人](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)、[GitLab 草稿合并请求](https://docs.gitlab.com/user/project/merge_requests/drafts/)。
