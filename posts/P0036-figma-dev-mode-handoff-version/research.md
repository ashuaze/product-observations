# P0036 研究底稿

核查日期：2026-11-12（北京时间）。P34–P40 周期问题：多人协作中，产品怎样让下一棒知道该做什么？

## 中文审稿摘要

- Figma 的 Ready for dev 标记可交给开发实现的对象；交付后部分编辑会让它进入 Changed。Dev Mode 聚焦视图支持查看旧版本、复制特定版本链接及与最新版比较。
- 直接修改画框与修改它引用的共享值，可能呈现不同的状态信号。Figma 明列已绑定变量或样式的值变化、来自共享库的组件实例更新等不触发 Changed 的情况。
- 实时稿适合双方都在迭代、变更能及时沟通的工作；需要按同一版验收时，建议在工单里保留约定版本和关键依赖值，再明确谁负责确认变更。
- 文档支持规则和入口，不证明返工会减少，也不保证某版链接会锁定全部共享依赖。本次未做账号实测。

## 中文研究底稿

**研究问题。** 一个日期选择器已交接开发，随后间距变动。开发要跟实时稿，还是按双方原先同意的版本完成？同一个控件、同一交付任务下，比较两条路径，并分别用直接改画框与改既有绑定的间距变量触发。间距示例是推演，不是体验记录。

**事实。** Figma Dev Mode 的 Ready for dev 可标在区段、画框和组件；对已标 Ready for dev 或 Completed 的设计，适用修改可自动触发 Changed。文档明确排除已绑定变量或样式的值变化、来自共享库的组件实例更新及临时变化。状态操作需要 Full 或 Dev 席位；主动更新已变更设计的状态与追加通知有计划限制，官方状态文档列出 Education（K-12）、Organization、Government、Enterprise。不能推断每次编辑都会通知每位开发。[^status]

在聚焦视图，版本历史按当前设计筛选，可打开旧版本、复制特定版本链接或与最新版对照。Inspect 入口的历史时间线有范围限制：文档说明随时间比较顶层画框才显示历史时间线。链接能指出约定的历史版本；文档并未证明它会冻结所有外部依赖。[^focus][^compare]

| 同一控件的交接方案 | 适合 | 代价或失败条件 |
|---|---|---|
| 实时画框 + 约定重交接条件 | 双方希望采用最新改动，实施成本低且能快速确认 | 改共享变量时可能没有状态提示，开发者可能混用新旧规格 |
| 工单链接约定版本 + 记录关键共享值 | 验收要可复核，或变动会影响实现、测试和签核 | 若修正应立刻应用，旧链接可能把人留在已知过时的版本；需明确替换链接的人和时点 |

**反例与新增判断。** 共享变量更新可能是团队刻意让所有控件同步的行为；在小改动、低返工成本的迭代里，每次冻结都可能拖慢有意同步。反过来，只有 Ready 徽标也不能证明约定规格没变。回读 [P34](../P0034-github-draft-pr-review-handoff/research.md) 和 [P35](../P0035-zendesk-waiting-ticket-statuses/research.md)：两篇分别问谁接手和谁负责推进；本期新增「接手的人具体按哪个版本工作」这一项。

**待验证。** 用两组相同的交接任务分别采用实时链接与约定版本加关键值，再注入直接编辑与共享变量变化。记录开发选错版本率、发现变化所需时间、采用应跟进修正的延迟，以及重复确认次数。若约定版本没有减少误用，却推迟了应采用的修正，就缩小它的使用范围。未登录产品或运行此测试，没有账号表现或行为因果结论。

## 发稿前检查

- 固定日期选择器和实现任务，只改变交接方式或改动路径。
- 以变量变更不触发 Changed 约束论点；保留实时同步更合适的反例。
- 读者可按返工与验收成本选择基准，并验收直接改动与依赖改动两条路径。
- 官方 twitter-text 3.1.0 加权长度（含序号及随帖 URL）：英文 222 / 210 / 184 / 228；中文 136 / 138 / 122 / 160。各条均不超过 280。
