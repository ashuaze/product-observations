# P0037 研究底稿

核查日期：2026-11-13（北京时间）。P34–P40 周期问题：多人协作中，产品怎样让下一棒知道该做什么？

## 中文审稿摘要

- 在 Google Docs，评论里的行动项和进入 Google Tasks 的任务是不同的功能。两种指派都面向工作或学校账号。
- 从清单行创建任务后，只删清单行不会清除对方列表里的任务；删除任务本身才会移除该待办。
- 保留待办有合理用途：纪要重组时，承诺未必改变。但如果工作已经取消，仍然活跃的待办可能引发误执行。
- 建议把局部修订留在原文旁，把需要离开文档后继续追踪的交付放入任务列表，并验收取消路径。本期仅核查文档，未测效果。

## 中文研究底稿

**研究问题。** 财务同事在评审预测文档时，作者需要他核对一个数字，或者周五另发一份更新。如何在文档里给他上下文，同时让仍有效的承诺在会后可找回？在同一个「周五发新版预测」任务、同一作者和接手者下，比较两种承载方式。示例为推演。

**已核查的规则。** 电脑端可用工作或学校账号，在文档内的评论中提及某人并显式勾选指派；接手者会收到邮件。普通 @ 提及本身也能发通知。评论行动项支持改派、标记完成，文档可查看未结行动项。[^comments] 另一个入口是文档内创建任务（如从清单创建），可指派自己或同域人员，选填日期，并进入接手者的个人 Google Tasks 列表。若只删清单行，任务仍可留在接手者列表；在文档里删除任务本身才会从列表移除，未完成的任务还会触发邮件通知。修改清单文字但未更新任务、在 Tasks 改标题或回滚文档，都可能产生不一致提示。[^tasks]

| 同一交付如何交接 | 收益 | 代价与失败条件 |
|---|---|---|
| 用文档评论行动项指派，并写清周五交付 | 讨论与所涉内容在一起，接手者可以就地问清楚 | 若接手者只在任务列表工作，作者不能把评论通知当作该列表中的待办 |
| 从清单生成任务并设日期 | 接手者可在文档外找到工作；整理纪要不必撤销承诺 | 文档文字、任务及取消操作可能不同步；若把删清单当取消，接手者可能继续执行 |

**反例与边界。** 单一「删行就取消」规则看似能防止旧任务，却可能在纪要归档或重新排版时取消一项仍有效的交付。反之，在文本更改频繁、任务只为修改本段而设的团队，把每个小修都推入待办列表会增加核对成本。文档列明的是电脑端工作/学校账号行为；不外推到个人账号、跨组织指派或所有客户端。也不把发送邮件等同于对方理解、接受或执行。

**新增判断及验证。** [P35](../P0035-zendesk-waiting-ticket-statuses/research.md) 把当前阻塞者和跟进人拆开，[P36](../P0036-figma-dev-mode-handoff-version/research.md) 把交接对象与所用版本拆开；本期把「来源文档是否仍在」和「承诺是否有效」拆开。比较同一交付的评论与任务路径，分别模拟整理纪要、正式取消。记录下一班能否找回仍有效任务、取消后误执行率，以及作者发现和修复不同步的耗时。如果团队日常就回看该文档，独立任务未改善找回率却增加误执行或维护成本，就优先保留文档内行动项。未做真实账号实测，无效果量或账号运营数据。

## 发稿前检查

- 对照固定同一交付，区分评论内行动项与独立待办；用整理纪要但保留承诺检验自动取消方案。
- 功能规则由官方文档支持；「何时放进独立列表」是可通过找回率、误执行率和维护时间推翻的建议。
- 读者可按工作需要出现在哪里选择承载方式，再验收承诺取消是否传到接手者的工作入口。
- 官方 twitter-text 3.1.0 加权长度（含序号及随帖 URL）：英文 204 / 250 / 248 / 241；中文 138 / 161 / 167 / 144。各条均不超过 280。
