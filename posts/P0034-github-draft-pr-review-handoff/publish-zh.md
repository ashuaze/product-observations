### 1/5

1/5 把半成品放出来，和请别人接手，不一定是同一个动作。GitHub 的草稿 PR 允许团队先看到改动，作者可以晚一点再发出正式评审请求。

### 2/5

2/5 草稿 PR 不能合并；标成可评审后，GitHub 才会自动向相关代码负责人请求评审。仓库如果要求审批，审批依然要做。三个动作可以分开：看见改动、开始评审、允许合并。

### 3/5

3/5 比如你在改结账流程，还没决定老购物车要不要兼容。先贴草稿，找能拍板的人回答这一个问题。如果改动已经值得整体评审，就现在发出请求，没必要等到每个细节都打磨好。

### 4/5

4/5 草稿也需要反馈。GitLab 的草稿和标为就绪的合并请求默认运行相同的流水线。先让测试指出哪里坏了，团队可以晚一点再花时间做完整评审。

### 5/5

5/5 做一个「准备好」按钮前，先写清楚它会让谁开始做什么。再看两笔账：评审者花在本就打算重写的改动上的时间，以及作者卡在未决问题上的时间。若评审变少但等待变长，就给草稿一个明确求助的入口。
